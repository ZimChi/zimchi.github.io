Using a Local Proxy to Protect API Keys from Supply-Chain Attacks

Chielo Zimmerman • October 5, 2026

In September 2026, researchers reported that the npm plugin @memtensor/memos-cloud-openclaw-plugin had been compromised to deliver a credential stealer. Each time the plugin ran, it collected tokens, passwords, and API keys from the application's environment and sent them to an external server.

This attack shows why sensitive credentials don't belong in an untrusted application runtime, especially one with many unaudited dependencies. In my previous post, I wrote about using Docker to contain supply-chain attacks. This post covers how I keep credentials away from the code running inside that container. The approach is simple: the application never sees the secrets at all.

A trusted local proxy

Instead of launching the application with API_KEY as an environment variable, route its requests through a trusted local proxy, which holds the key and attaches it to outgoing requests. If the application is compromised, there is no key in its environment to steal.

Docker Compose handles the internal routing

The Docker configuration maps the remote API hostname to the proxy container's IP address on a private bridge network. The application is unaware of this and sends and receives requests as it normally would. 

services:
  token-injector-proxy:
    build:
      context: .
      dockerfile: token-injector-proxy/Dockerfile
    container_name: token-injector-proxy
    env_file:
      - ../secrets/proxy.env
    networks:
      secure-api-net:
        ipv4_address: 172.20.0.10

  untrusted-application:
    build:
      context: .
      dockerfile: application/Dockerfile
    container_name: untrusted-application
    ports:
      - "3000:3000"
    volumes:
      - .:/app
    networks:
      - secure-api-net
    extra_hosts:
      - "api.example.com:172.20.0.10"
    depends_on:
      - token-injector-proxy

networks:
  secure-api-net:
    driver: bridge
    ipam:
      config:
        - subnet: 172.20.0.0/16

A local proxy written in Go

The proxy itself is built using only the Go standard library, which keeps it transparent and minimizes dependency risk. 

package main

import (
	"log"
	"net/http"
	"net/http/httputil"
	"net/url"
	"os"
	"time"
)

type upstream struct {
	token string
}

var upstreams = map[string]upstream{
	"api.example.com": {os.Getenv("API_KEY")},
}

func main() {
	proxies := make(map[string]*httputil.ReverseProxy, len(upstreams))

	for host, up := range upstreams {
		if up.token == "" {
			log.Fatalf("no API key configured for %s", host)
		}

		target, err := url.Parse("https://" + host)
		if err != nil {
			log.Fatalf("invalid upstream %s: %v", host, err)
		}

		proxies[host] = &httputil.ReverseProxy{
			Rewrite: func(pr *httputil.ProxyRequest) {
				pr.SetURL(target)
				pr.Out.Header.Set("Authorization", "Bearer "+up.token)
			},
		}
	}

	handler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		p, ok := proxies[r.Host]
		if !ok {
			http.Error(w, "unknown host", http.StatusForbidden)
			log.Printf("%s %s host=%s status=403 dur=%s", r.Method, r.URL.Path, r.Host, time.Since(start))
			return
		}
		p.ServeHTTP(w, r)
		log.Printf("%s %s host=%s dur=%s", r.Method, r.URL.Path, r.Host, time.Since(start))
	})

	srv := &http.Server{
		Addr:              ":443",
		Handler:           handler,
		ReadHeaderTimeout: 10 * time.Second,
	}

	if err := srv.ListenAndServeTLS("cert.pem", "key.pem"); err != nil {
		log.Fatalf("server failed: %v", err)
	}
}

The result

The solution is a trusted Go proxy with minimal dependency risk that holds the API key in its memory, so the untrusted application never has anything to leak.
